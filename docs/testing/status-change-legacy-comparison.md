## 5. What was changed to match legacy

**Server** (`server/src/modules/hr/personal-status/`)

1. **Read and auto-fill fixed:** `START_DATE` and the `*_SIGN` columns are VARCHAR2. They are now read
   with `TO_DATE(... DEFAULT NULL ON CONVERSION ERROR, 'DD-MON-RR', 'NLS_DATE_LANGUAGE=AMERICAN')`,
   and `START_DATE` is written as `DD-MON-RR` text. On TEST, read now works for 49/49 rows (was 3/49)
   and auto-fill for 49/49 employees (was 6/49). 45/45 stored start dates round-trip to identical text.
2. **Server-computed values:** the employee snapshot (name, nationality, section, department, start
   date, current position, pay items, `OLD_TOTAL`) comes from auto-fill and is never read from the
   body. On update it is recomputed only when `empNo` changes. `FORM_DATE` = today (Asia/Riyadh)
   and `ARB_DATE` = its Hijri date (legacy `ar-TN-u-ca-islamic` format), both set on create only.
   `NEW_TOTAL` = sum.
3. `OLD_TOTAL` = master `TOTAL_SALARY` (branch A), as legacy.
4. Revised position accepts `POSITION_NAME` or `JOB_TITLE` (the auto-filled default), max 100.
5. Amounts: digits with ≤ 2 decimals and ≤ 7 characters. Current family status is editable (S/M/blank;
   omitted keeps the snapshot or stored value). Revised grade/level are optional (≤ 50).
6. Identity `HEADER_ID` with `RETURNING`, then `REF_NO` in the same transaction. Removed `MAX+1` and
   its retry loop: the table has no unique key, so that retry could never fire.
7. Record access on read/update/delete: creator, HR (fail-closed), or same department
   (`ORGANIZATION_ID`) with `HR.PERSONNEL_RECORD_CHANGES:VIEW`; otherwise 403. The list uses the same
   scope. Update and delete are **draft only** (409 `PERSONNEL_RECORD_CHANGE_NOT_DRAFT`).
8. List adds the legacy `PENDING_AT` column (read-only subquery on `XXPHP_WORKFLOW`, `MSG_TYPE='RCF'`,
   open, no `TYPE_PARAM`; TEST: 2 rows, matching the 2 open notifications).
9. `personalStatusChange.rules.js`: `submitProblems` (validate-for-submit), `hijriDate`,
   `referenceNumber`, `payTotal`, `businessToday`.
10. `api.routes.js`: the service receives `holds` (permission check for same-department access).
11. OpenAPI updated (scope, 409, server-owned fields, `pendingAt`, grade/level, amount format).

**Client** (`client/src/features/hr-employee-services/`)

1. Employee pick: revised position and family status from the current record; revised amounts kept
   (`0` on a new form). Before, every current value was copied.
2. Current family status is an editable select (legacy `OLD_MARITAL_STATUS` input).
3. Amounts: legacy filter + `maxLength` 7; grade/level are optional text inputs (no longer disabled
   selects); position and family status marked required.
4. Effective date before the start date is a note, not an error. The "must change something" rule is
   removed (legacy has none).
5. Only drafts are editable (`isRecordChangeLocked`).
6. Status and signature colours (Approved green, Rejected red, with the signature date); `ARB_DATE`
   shown as saved.
7. Legacy family-status values (`Married`, `single`, `m`, …) read as S/M.
8. Payload sends only the answers (no snapshot, form date or Hijri date).
9. `validateRecordChangeForSubmit` (legacy submit rules; not wired).
10. Print sheet with the whole legacy form.
11. Change Requests list: legacy columns, legacy status tabs, CSV export (reuses `toCsv`/`withBom` from
    `hr-recruitment/report/periodwiseModel.js`; no new dependency), print.
12. README, texts and CSS updated.

Shared components were **not** changed. The only shared text change is a `REJECTED` label added to
`ES_COMMON_TEXT.approval`. No other form was touched.

## 8. Legacy workflow (for the shared workflow design)

**Trigger.** Submit button (shown for a saved request whose status is not INPROCESS, APPROVED or
ACCEPTED, so DRAFT and REJECTED requests can be submitted) → confirm "Do You want to send Request in
Workflow ?" → `GET Rec_flow/submit?header_id=`. The server refuses `APPROVED`, `Approved`,
`Accepted`, `Inprocess` and `INPROCESS` ("Request is X. Cannot Re-initialize Workflow"). It checks
no field values.

**Requester.** `getUserProfile(CREATED_BY)`: full name and e-mail from `XX_DIGI_EMP_MASTER` where
`USER_ID = CREATED_BY`.

**Route (3 steps, `last_step = 3` hard-coded).** `getExpenseFlowRec(request.USER_ID, step)` looks up
the department of the person whose master `USER_ID` equals the request's `USER_ID` column:

- Department containing *operation, production, maintenance, toolroom* or *sales*: step 1 Operations
  Director, step 2 HR & Administration Manager, step 3 General Manager.
- Otherwise: step 1 HR & Administration Manager, step 2 General Manager, step 3 General Manager (the
  same person twice).

The approvers are three named people hard-coded in the SQL (employee number, name, e-mail from
`DUAL`). They are not reproduced here and must become configuration. `USER_ID` is NULL on 40/49 TEST
rows, so in practice the second route is used. An earlier routing query over `XX_DIGI_PERSON_INFO` /
assignments / org group (`SHARED SERVICE`, `SALES`) is still built but never executed.

**Delegation.** `Workflow_model->delegatedUser(recipient, formCode)` swaps the recipient and marks
the row "Delegated" (`DEL_CODE`, `DEL_FOR`).

**Submit.** New notification and group IDs (`getMaxNotificationID`, `getMaxGroupID`). An HTML e-mail
goes to the step-1 approver: summary (Emp No, Name, Section, Department, Current Salary =
`OLD_TOTAL`, Revised Salary = `NEW_TOTAL`, Effective Date), links Form / Approve / Reject / Forward /
Reassign / Request Information (`Zmailer/request_status?…&action=1|0`, `Zmailer/forward`,
`…&reassign=reassign`, `Zmailer/request_information`) and the notification history. Subject
"PERSONNEL RECORD CHANGE FORM - Request Submitted By {requester}". **Only if the mail is sent:**
`callXXPHP_WORKFLOW` (msg type `RCF`, form link `Rec_change/index/`, workflow path
`index.php/rec_flow/workflow`, steps 3, current 1) and `STATUS = 'INPROCESS'`. A mail failure
leaves the request unchanged.

**Action** (`POST Rec_flow/workflow`, JSON `header_id, gid, nid, action (1/0), workflow_comment`):

1. The notification must still be open (`checkRequestOpen`), and the request must not be in RFI mode
   ("Request is in RFI Mode, Pending At - X").
2. Next recipient: step `current + 1` approver while `≤ 3`, else the requester (delegation applied).
3. **Approve, step < 3:** mail the next approver ("Approved By {approver}"); close the current
   notification; `STATUS = 'INPROCESS'`; insert the next workflow row; stamp the step.
4. **Approve, step 3:** mail the requester; insert the closing row (step 4); close both
   notifications; stamp; `STATUS = 'APPROVED'`.
5. **Reject, any step:** mail the requester ("Rejected By"); close the notification; stamp
   `REJECTED`; `STATUS = 'REJECTED'`.
6. Step stamps (`updateAction`): step 1 → `HR_ADMIN`/`HR_ADMIN_SIGN`, step 2 → `VP`/`VP_SIGN`
   (hidden on the form), step 3 → `PRESIDENT`/`PRESIDENT_SIGN`. The value is `APPROVED` or
   `REJECTED`; the date is `date('d-M-y')` text. The form labels them "Noted by HR & Admin. Manager"
   and "Approved by President", although step 1 can be the Operations Director and step 3 is the
   General Manager.
7. No "return to requester" action exists. RFI (request information), forward and reassign are
   handled by the shared `Zmailer`. A rejected request is re-submitted from step 1 with a new group
   ID; old stamps are not cleared.

**Stored values (TEST).** `XX_REC_CHANGE.STATUS`: DRAFT 11, INPROCESS 2, APPROVED 29, REJECTED 7.
`HR_ADMIN`: APPROVED 30, REJECTED 7; `VP` and `PRESIDENT`: APPROVED 29. `XXPHP_WORKFLOW` (`RCF`):
`NUMBER_OF_STEPS` 3, steps 1–4, `STATUS` `Open`/`Close` (2 open).

**Mail transport.** Office 365 SMTP with a mailbox and password hard-coded in `Rec_flow.php`
(rotate; use configuration secrets in the new design).

## 9. Assumptions and open questions

1. Form 1110 = legacy `Rec_change` / `RCF` (matched by name; the number is not in legacy code).
2. `ARB_DATE`'s meaning is "Hijri date of the form date"; legacy's refresh-on-save is treated as a
   side effect (B8).
3. Current family status: choices limited to S/M (master values are S/M only on TEST: 124 S, 20 M,
   3 NULL). Legacy accepted free text.
4. Same department = same current `ORGANIZATION_ID` in `XX_DIGI_EMP_MASTER` (as Probation).
5. HR = the fail-closed `XXZP_HR` TAG check of `hr-identity-mapping.md` §2. That doc's open question
   (3 of 12 tags hold a details user ID) applies here too.
6. The employee and position lookups stay unscoped (legacy). They expose employee numbers and, through
   auto-fill, salaries to any holder of `HR.PERSONNEL_RECORD_CHANGES:VIEW`. Should auto-fill need
   `CREATE`/`UPDATE`, or HR?
7. Legacy requests whose stored employee has no current master row still open (snapshot is stored);
   changing the employee on such a draft needs a current employee.
8. The demo adapter for record changes is test-only (the live page always uses the API); its
   `SUBMITTED` status was left as is.
9. Running the identity insert on TEST was not done (no writes); the statement was parsed only.
